# Music Library – agent notes

Native macOS music library app (SwiftUI) built with SwiftPM only; no Xcode project, no third-party dependencies. Works with Xcode or just the Command Line Tools. MIT licensed.

`MusicLibraryCore` also builds for iOS 27, for the planned iPhone companion app (`docs/ios-companion-plan.md`). Parts that can't run there are wrapped in `#if os(macOS)`: running ffmpeg/ffprobe/fpcalc (`Tools.swift`, `TagReader`/`TagWriter`/`ImageTools`, `ImportService`, `AcoustIDClient`, `AlbumCover.swift`, `CDRipper`/`CDImporter`, `AccurateRipAudio.swift`), CoreAudio output switching (`CoreAudioOutput.swift`) and parsing library catalog pages (`LibraryCatalogParser.swift` uses `XMLDocument`; `CatalogEnricher.details`). Keep new Core code platform-neutral, or guard it the same way. `Database(snapshotAt:)` opens an exported or synced `library.sqlite` read-only (no migrations; refuses a newer schema).

The iPhone app (`iOS/MusicLibraryMobile.xcodeproj`, the repo's only Xcode project; the Mac app stays SwiftPM-only) depends on the local package for `MusicLibraryCore`. Its sources are a synchronized folder (`iOS/MusicLibraryMobile/`): new files there are picked up without editing the project. The target uses Swift 6 with main-actor default isolation, so code that runs off the main thread needs `nonisolated`. It reads the library from its Documents folder (`LibrarySnapshot`: the whole library with its cached artist/album info, photos, plays, play totals, ownership and `CollaborationGraph`, plus `presentIDs`, the tracks whose files are on the phone: only those play (`playable`), the rest are dimmed and can be downloaded; `findRoot` accepts `Music Library`, Documents itself, or an export dragged in under any name) and reloads when the app becomes active. `PhonePlayer` (an `AVQueuePlayer`; background audio, lock screen controls) switches the audio session to each song's sample rate before playing it (off the main thread; the session is deactivated and reactivated when the rate differs from the last song's; `AVAudioSession.sampleRate` lags behind the hardware after a change, so the output shown is read again after playback starts), preloads the next song for a gapless transition only when it has the same rate, restarts the song at its rate when a DAC is plugged in mid-song, and pauses when it's unplugged. Open files with `AVURLAssetPreferPreciseDurationAndTimingKey` (AVFoundation otherwise estimates positions in FLAC files without a seek table) and seek the current item, not the queue player (a seek can otherwise land in the preloaded next song). `PhoneModel` overlays the outbox (likes, plays, and ownership changes older versions left there) on the snapshot, computes Insights in the background, tracks `Availability` and download/remove requests (`SyncRequestQueue`, Application Support `sync-requests.json`; removing deletes the files at once with `SyncReceiver.delete`, covers stay), and wires the player to the shared `Scrobbler` (flushes on becoming active and when the network returns) and saves the queue to Application Support `player-state.json` (restored paused, like the Mac). Tabs: Library (All Music / On This iPhone), Insights, Sync, Search; every tab's stack is a `LibraryStack` (routes `LibraryRoute`, `AlbumSummary`, `ArtistSummary`, `DNARoute`, `QueryRoute`; `@Environment(\.openRoute)` pushes from menus). `AlbumPage`/`ArtistPage` mirror the Mac's pages (`AvailabilityBar` for Download/Remove), `MusicDNAViews.swift` and `InsightsViews.swift` (and its Listening/Owned files) port the Mac's; `PhoneConcerts` uses the concert settings the Mac hands over. Sample library (for App Review and anyone without the Mac app): `SampleLibrary.bundle` in `iOS/MusicLibraryMobile/` is a library folder made by `scripts/make-sample-library.sh` (the `SampleLibraryMaker` target: songs synthesized by `SongSynth`, covers and artist pictures drawn by `Artwork`, fictional artists in `SampleCatalog`, imported with `ImportService`, plus plays, likes, ownership and playlists). `PhoneModel.showSample` opens it read-only in place (`LibrarySnapshot(datesRelativeToNow:)` moves its history up to today) only while Documents has no library; `isSample` routes likes and plays to `sampleOutbox` (never synced), skips Last.fm, keeps its own player state and hides Download/Remove, and your own library arriving (or Hide) drops all of it (`forgetSample`). `SampleLibraryTests` open the committed bundle. Settings (gear on the Library tab): sample-rate matching, output, Last.fm (the phone's own API key/secret and session, in its keychain). Signing: `iOS/Signing.xcconfig` includes the uncommitted `iOS/Local.xcconfig`, which holds `DEVELOPMENT_TEAM` (and, for a Personal Team, an `APP_BUNDLE_ID` unique to you; the targets' bundle IDs and `APP_GROUP_IDENTIFIER`, `group.$(APP_BUNDLE_ID)`, derive from it, so don't set `PRODUCT_BUNDLE_IDENTIFIER`). The version of all four targets is `iOS/Version.xcconfig` (`MARKETING_VERSION`, kept at the Mac release's; `scripts/testflight.sh` sets the build number). `PrivacyInfo.xcprivacy` in `iOS/MusicLibraryMobile/` and `iOS/MusicLibraryWatch/` declares the required-reason APIs (user defaults, file timestamps, disk space) of the code in each, `MusicLibraryCore` included: declare any new one there. Free disk space may not leave the phone, so the Mac sends what a sync `needed` (`SyncPlanSummary`) and the phone refuses a sync that doesn't fit (`SyncHello.freeSpace` is only read from older phones).

Widgets and the Apple Watch app (same Xcode project): they show a `Glance`, a small Codable summary (library counts, `week`/`month` listening, owned albums, now playing, rediscover) in the Foundation-only `MusicLibraryGlance` package target (also `GlanceLink` `musiclibrary://` URLs, `GlanceCommand`, `GlanceMessage` keys, `GlanceFormat`), built by `Glance.build`/`Glance.nowPlaying` in Core (`GlanceBuilder.swift`, `GlanceTests`). The phone's `GlanceFeed` rebuilds it off the main thread (debounced; only Now Playing when just the player changed) and writes it with JPEG thumbnails named `Glance.coverName(albumKey:)` to `GlanceStore.shared` (`Glance/` in the app group container; the group ID is the Info.plist key `MusicLibraryAppGroup`), then reloads widgets, and `WatchLink` sends it to the watch (application context, plus a message while reachable; the watch asks for covers by message while the phone is reachable and gets 160 px JPEGs in the reply, a few per message). Commands (widget buttons, watch) go through `PhoneModel.perform`, which loads the library first (background launches) and writes the summary before returning (iOS reloads a widget right after its intent). Widget buttons are `AudioPlaybackIntent`s in `iOS/Shared/PlaybackIntents.swift` (compiled into the app and the iOS widget extension, which defines `WIDGET_EXTENSION`); they run in the app's process and use `PhoneModel.shared`, because SwiftUI may not have created the app yet. `iOS/MusicLibraryWidgets/` is compiled by both widget extensions (`MusicLibraryWidgets` for iOS: Listening, Now Playing, Recent Purchases, Rediscover, Library; `MusicLibraryWatchWidgets`: accessory families of Listening, Now Playing and Purchases), with `#if os(iOS)` around home-screen families and intents; those targets use Swift 6 without main-actor default isolation. `iOS/MusicLibraryWatch/` is the watchOS app (`WatchModel`: the summary in its own app group container for the complications, commands with replies; WatchConnectivity callbacks are `nonisolated`/`@Sendable`). The watch can't play music itself; it's a remote.

- `Sources/MusicLibraryCore`: all non-UI logic (SQLite, tags via ffprobe/ffmpeg, organizer, MusicBrainz/AcoustID/CoverArt clients, import, export, search, stats).
  - Search: `Search.swift` parses the query language (`SearchQuery`, filter keys in `SearchFilterKey.all`); `SearchIndex.swift` is an immutable in-memory index (matching, ranking, completions, spelling correction). The app rebuilds it off the main thread on every library reload; smart playlists are saved query strings evaluated against it.
  - `Themes.swift`: theme palettes (8 base colors each; card, separator and chart ramps are derived). `ThemeTests` enforce contrast for every palette, so new themes must pass them. The app applies a theme with `.themedRoot(_:)`; use `.subtext` instead of `.secondary` for secondary text (`Text` ignores custom hierarchical styles). Sidebar counts use `.sidebarBadge(_:)`, not `.badge`: themes draw their own pill (`badgeFill`/`badgeText`) because the native badge's number is too faint on some palettes.
  - `LastFM.swift`: signed Last.fm client (injectable transport for tests), `ListenTracker` (scrobble rules), `ScrobbleQueue` (persisted to Application Support). `Scrobbler.swift` (`@Observable`, shared by the Mac and iPhone apps) connects them to the player: account (browser authorization through an injected `openURL`), now playing, the queue with retry and backoff.
  - `ArtistInfo.swift`: artist info from MusicBrainz (url-rels, genres), Wikidata, Wikipedia summaries and Last.fm; pure parsers and `ArtistInfo.assemble` are tested with real fixtures, `InfoFetcher` does the network calls (artists and albums). `ArtistResolver` picks the MusicBrainz artist (multi-artist credits need a confident name match). The app's `ArtistInfoStore` caches it in the `artist_info` table and `<root>/Artist Images`. External URLs (MusicBrainz relations, Wikipedia/Last.fm pages, and anything read back from the `artist_info`/`album_info` caches) are untrusted: parse them with `URL(webLink:)` and only pass `url.webLink`/`isWebLink` URLs (http/https with a host) to `Link`/`openURL`.
  - `ArtistPhotos.swift`: photos the user can pick for an artist. `ArtistPhotoFinder` (injectable transport) searches Deezer's artist API (no key; pictures with an empty image hash are placeholders) and Wikimedia Commons, and lists the artist's linked Deezer artist (MusicBrainz url-rel) and Wikipedia article images first; Wikimedia files are resolved to a 1200 px rendition when picked. Only https images from Deezer/Wikimedia hosts are downloaded (`ArtistPhotoParser.isPhotoURL`). Fixtures `deezer_*`, `wp_images_*`, `commons_search_*` are real responses. The chosen photo (`ArtistPhotoChoice`) is saved in the `artist_photos` table, apart from `artist_info`, so updating the info never replaces it; its file goes in `Artist Images` under a new name each time (views reload by file name), and rows are untrusted (`isSafeFileName`). The app's `ArtistPhotoSheet` (artist page: toolbar, hover on the photo, or dropping an image on it; artist grid context menu) shares file/drag/clipboard loading with `AlbumCoverSheet` via `ImageInput`; show photos with `ArtistInfoStore.imageFile(for:)`/`imageURL(for:)`, which prefer the chosen photo.
  - `AlbumInfo.swift`: album info from the MusicBrainz release group (rating, filtered genres, review links), the matched release's track list, Wikipedia and Last.fm; `AlbumTracklist.merge` lines the release up with the library's tracks. Cached in `album_info` by `AlbumInfoStore` (opening an album fetches it first).
  - `MusicDNA.swift`: `CollaborationGraph`, people from credits/tags/track artists (merged by MusicBrainz ID, then normalized name; non-musical release credits like photography are skipped) linked by shared tracks, plus the capped breadth-first neighborhood and radial layout shown on the Music DNA page. Rebuilt with the search index. In the UI, show people's names with `PersonLink`/`PersonLinks`/`PeopleRow` (pass `model.showMusicDNA` as `open`) so they open Music DNA.
  - `PlayQueue.swift`: the Spotify-style play queue (the list playback started from, plus songs queued with Play Next, which always play next; Add to Queue appends to the end). `Player` wraps it; `QueueView` shows it in the window's inspector. The queue and position are saved on quit (and at each track change) as a `PlayQueue.Snapshot` of track IDs in Application Support (`player-state.json`, `AppModel.savePlayerState`) and restored paused at launch; a restored song isn't loaded (no output-format change, no play recorded) until it's played.
  - Liked songs: the `liked_tracks` table (track id, liked date; cascades when a track is removed), `AppModel.likedDates`/`setLiked`. Liked Songs is a built-in playlist (`SidebarItem.likedSongs`, `ExportItem.likedSongs`, most recently liked first) that can't be renamed or deleted. Show the heart with `LikeButton(model:track:)` (safe in `Table` cells) and `LikeMenuButton` in song context menus.
  - Listening history: the `plays` table (one row per listen, `counted` = met the scrobble rule), recorded by `AppModel` from player events.
  - `LibraryExport.swift`: `LibraryExporter` copies tracks to another folder using the library's layout (data only, via a hidden partial file and a rename; it never overwrites or deletes), writes `Playlists/*.m3u`, and can replace `<dest>/library.sqlite` with a `VACUUM INTO` snapshot (bringing `Artist Images` up to date with it). `ExportPreview` scans a destination's `Music` folder and merges it with the plan, per album folder, for the Export List's split view. The app's Export List (`ExportItem`, `ExportViews.swift`) collects albums, songs, artists and playlists and resolves them to tracks at export time; the destination is a setting (`AppModel.exportDestination`). `PlaylistExporter` (in `Import.swift`) is the older one-folder-per-playlist export.
  - `LibrarySort.swift`: `AlbumSort`, the Albums grid's orders on the Mac and iPhone (`albumSort`), and `SongSort`, the iPhone Songs list's (the Mac song table's columns plus Date Added; empty values last, ties in library order).
  - `Stats.swift`: `LibraryStats`, everything shown in the Library pane of Insights, computed in one pass with data-driven list sizes and bucket granularity.
  - `ListeningStats.swift`: `ListeningStats`, the Listening pane of Insights, from the `plays` rows (`Database.plays()`) for one period (7 days, 30 days, 12 months, all time): top songs/artists/albums/genres, activity over time, a weekday × hour clock, eras vs the library, skips, streaks and forgotten favorites. `AppModel.loadListeningIfNeeded` computes it in the background and refreshes it when `historyVersion` (bumped per recorded listen) changes.
  - `AlbumOwnership.swift`: albums you own (`AlbumPurchase`: a `format`, CD or download, optional purchase day, price and, for a CD, label number, the sticker on the case; the app suggests `nextLabelNumber`), saved per album key (`SearchIndex.albumKey`) in the `album_ownership` table, apart from the tracks, so re-importing keeps them. `label_number` and `format` (NULL = CD) were added on open without a schema version change (older phones read the other columns by name), so `albumPurchases` reads snapshots without them. On the collection branch the Mac remakes the table once with defaults no app writes (`Database.markLegacyWriters`: `format` 'pre-1.19'/'pre-1.18', a trigger nulls the label's), so `CollectionLegacy.reconcile` can tell a column an older Mac left out from one it cleared: always name every column when writing it. Formats and label numbers are set on the Mac only: they aren't in `AlbumPurchase`'s Codable form (sync events), and `applySyncEvents` keeps the Mac's when it applies a phone's ownership change. Songs bought as downloads (`TrackPurchase`, entered on the Import page, per song or a batch total split with `TrackPurchase.split`) are in `track_purchases` (created on open, cascades with the track); `AlbumPurchase.including(songs:tracks:in:)` adds a download for each album without a record whose songs were bought, which is what `AppModel.purchases` and `LibrarySnapshot.purchases` hold (`AppModel.purchaseRecords` is only what you said on the album page or when ripping). `OwnershipMark` says how a cover shows it. `PurchaseDay` is a calendar day with no time zone; prices are `Decimal`, stored as POSIX decimal text in the locale's currency (`currencyCode` in the app). Rows are untrusted and read back with bad dates/prices as unknown. `OwnershipStats` is the Owned pane of Insights (library albums only). The app edits ownership on the album page (`AlbumOwnershipSection`) and when ripping a CD (`CDOwnershipPanel`; saved for the matched release when ripping starts, then on every change); `AppModel.purchases`/`purchasesVersion`, `loadOwnershipIfNeeded`.
  - `AccurateRip.swift`, `AccurateRipAudio.swift`, `RipChecks.swift`: checking rips against AccurateRip (accuraterip.com, no key). `AccurateRipDisc` identifies a disc from its TOC (audio track starts minus the 150-block lead-in, plus the freedb ID); `AccurateRipClient` downloads its `dBAR-….bin` (a 404 means the disc isn't listed; `AccurateRipPressing.parse`; fixture `accuraterip_dBAR-*` is a real response). `AccurateRipVerifier` finds where the rip lines up: the drive's read offset (±`AccurateRip.maxOffset` samples; macOS doesn't correct it), by sliding v1 checksums across every offset, and pressings holding the audio further apart (±`maxPressingOffset`, a real CD in the database is 5,574 samples off), by the sector 450 checksums at every offset, then the whole track's v1/v2 where one matches; audio beyond the disc's ends counts as silence, and reports per track accurate (with confidence), inaccurate (other tracks matched, this one didn't) or unknown. Samples are 16-bit stereo frames as one little-endian word, left in the low half. Audio comes through an `AccurateRipAudioSource`: `RipAudioSource` decodes library files with ffmpeg (`PCMDecoder`; needs the bundled ffmpeg's `s16le` muxer and `pcm_s16le` encoder) and reads only the needed samples of the disc's tracks (`CDTrackAudioFile`; macOS shows them as AIFF-C with little-endian `sowt` samples). Only lossless 16-bit 44.1 kHz stereo files are checked (`RipDiscMatcher.isCDAudio`): anything else would fail as misread. The loops over a track's samples are `while` loops on purpose: in a Debug build (`swift run`) a `for` over a range goes through generic witnesses and made an album check take minutes (time a check with a release build). Results, with the disc each track was ripped from, are saved per track in `rip_checks` (`RipCheck`; rows untrusted), a Mac-only table created on open without a schema version change, so synced and exported copies stay readable by phones on older versions (they refuse a newer schema). An album page's check considers every disc the tracks fit (`RipDiscMatcher.discs`: every track's exact length): those saved with its tracks and those MusicBrainz lists for its release (`MusicBrainzClient.discTOCs`). Several can fit, since discs whose tracks all start a few sectors later have the same lengths but are listed apart in AccurateRip (sometimes as a different pressing whose tracks differ), so each is checked and the one with the most accurate tracks wins (`RipChecker.score`). The app's `RipChecker` (`AppModel.rips`) checks right after ripping (`CDController.checkRips`, reading the tracks around the ripped ones from the disc; a disc with a misread track isn't auto-ejected) and from an album page's … menu; Ripping a track already in the library from the same disc (**Rip Again** on a misread one, or a checked "In library" row) goes through `CDController.ripInPlace`: the track is read straight from the disc bypassing the file cache (`CDTrackAudioFile.readAll`), and while AccurateRip says it's misread, read again up to `readPasses` (5) times, the reads combined sample by sample (`ReadVote`: the value most reads agree on; it stops after two identical reads) and checked from memory (`AccurateRipAudioOverlay`); from the third read, when that's still misread, `AccurateRipVerifier.repair` tries each damaged spot's versions from the reads (`ReadVote.spots`) in combination: AccurateRip's checksums add up each sample's contribution, so a meet-in-the-middle search finds the combinations matching a listed checksum, and one is kept when a second pressing's checksum matches too (or, from at most `maxSingleConfirmation` combinations, when none does); the result is written with `PCMEncoder.writeFLAC` and replaces the library file in place (same track ID, so plays, likes and playlists stay) unless it's still misread, or the earlier rip was accurate and the new one can't be confirmed; it never imports a second copy.
  - `AlbumCover.swift`: `AlbumCoverWriter` gives an album a new cover: `cover.jpg` in its folders (atomic write) and, optionally, the art embedded in its mp3/flac/m4a library files (`TagWriter.replaceEmbeddedCover`: remux with `-c copy` to a hidden temp file, then `replaceItemAt`; audio and tags kept). Paths go through `Track.coverURL`/`resolvedFileURL`. The app's `AlbumCoverSheet` (album page: toolbar, hover on the cover, or dropping an image on it) finds covers on the Cover Art Archive for the tagged release/release group and `MusicBrainzClient.searchReleases(album:artist:)` results, or takes a file, a dragged web image or the clipboard; `CoverImage.jpeg` converts to JPEG at most 1600 px. `AppModel.coverRevision` is bumped after a change; pass it to `CoverThumb(revision:)` so views reload the same cover.jpg.
  - `LibraryCatalog.swift`, `LibraryCatalogParser.swift`, `LibraryCatalogMatching.swift`: a public library catalog run on Aspen Discovery (default https://natick.minlib.net, Minuteman Library Network). Aspen's JSON API is IP-restricted, so the catalog is read like its website: `/Search/Results` (20 per page; filters `format`, `owning_location` (any of), `available_at`; negated filters are ignored), `getCopyDetails` (copies per library), `getRelatedManifestations` (editions with UPCs), the work page (contributors, contents), the Location facet popup (library list), `loginUser`, `getCheckouts`, and lists (`getSaveToListForm` for the patron's lists, `saveToList`, `/MyAccount/MyList/<id>` pages, `?delete=<entry>`). `CatalogParser` cuts result pages into one fragment per result before parsing (tidy HTML mis-nests them); fixtures `minlib_*` are real pages. `CatalogEnricher` matches a title on MusicBrainz by barcode (falling back to a release group search) and fetches its `AlbumInfo`; results are cached in `catalog_info`. `CatalogOwnership` says which library album a catalog title is (release group, then normalized title + compatible artist).
  - `ApplePreviews.swift`: 30-second song previews of library CDs you don't own, from Apple's iTunes Search API (no account or key). `ApplePreviewFinder` tries an Apple Music link on the MusicBrainz album, then barcodes (Apple's often differ from the CD's), then a search on artist and title (`ApplePreviewMatcher.bestAlbum`); `ApplePreviewMatcher.lineUp` matches Apple's songs to the track list. `ApplePreviewClient` spaces requests 3 s apart (Apple allows about 20 a minute), so previews are fetched only when a title's page is opened, never during scans. Results are cached in `catalog_previews`; preview and page URLs must be https on apple.com (`ApplePreviewParser.isAppleURL`, checked again when read back from the cache). Fixtures `itunes_*` are real responses. The app's `PreviewPlayer` (`AppModel.previews`) plays them apart from `Player`: previews never join the queue, history or Last.fm, and starting either one pauses the other.
  - `CDShopping.swift`, `CDShoppingParser.swift`: Shop for CDs (Mac sidebar **Shop for CDs**, album page … menu). `CDSearchQuery` builds a MusicBrainz release search (`barcode:` with and without a leading 0, else `catno:`, plus `format:CD`); album and artist match word by word, each word also as a prefix (`(release:green* AND release:riv*)`), so a few words of each find everything that has them, and `searchCDEditions` retries with any word (`loose`) when that finds nothing. An artist alone lists their discography instead: `searchArtists` (other close matches shown as chips), then `cdAlbums` browses the artist's album/EP release groups (paged, `CDDiscographyParser.sorted`: studio albums first, then live, other, compilations, EPs) and `cdEditions(releaseGroupId:)` looks up an album's CD editions when it's opened; `CDEditionParser` keeps releases with a CD medium and groups them by release group (`CDAlbum`, albums with an official edition first: bootlegs reuse barcodes). The user locks a `CDShoppingTarget` (one `CDEdition`, any CD edition of the album, or `init(byName:)` for a CD MusicBrainz doesn't list, from the "Search the stores by name" link: no Discogs, stores searched by the artist alone and listings kept when they hold half the typed title's words); `MusicBrainzClient.cdShopLinks` reads the release's and release group's url-rels for the Discogs release/master and Amazon ASIN (`CDShopLinks`). `CDShopURLs.requests` lists the pages to read: Discogs `/shop/list` (`release=` or `master=` + `formatName=CD`, `ships_to=US`, by price), eBay's Music CDs category (barcode, by price + shipping, and keywords), CDandLP and Alibris keyword searches; `browse` gives the store searches to open (also Amazon, Walmart, Half Price Books, Barnes & Noble). The sites are behind Cloudflare/eBay bot checks that refuse URLSession, so the app's `CDShopPageLoader` opens each page in a hidden WKWebView per store (persistent data store, one page at a time per store, 3 s apart; eBay's "Error Page" means load its home page and retry; Discogs draws its list with script and only the rows in view, so the view is 10,000 px tall and the loader waits for `article.msr-listing-card`) and returns the rendered HTML. `CDShopParser` (macOS, XMLDocument like the catalog's) cuts it into one fragment per listing; fixtures `shop_*` are real rendered pages with scripts and styles stripped. Listing and image URLs must be https on the store's domains (`CDShop.owns`). `CDOfferMatcher.filter` dedupes, drops other formats and lots, checks keyword results name the album (and, except eBay, start with the artist), promotes those carrying the edition's catalog number or barcode to `.edition`, and sorts best match then cheapest total in dollars (`ExchangeRates` from Frankfurter's ECB rates, no key, cached a day; Discogs' own "about $" total when shown; unknown shipping counts as none). `DiscogsMarketStats` is Discogs' public `/marketplace/stats` summary. The app's `CDShopStore` (`AppModel.cdShop`) keeps results in memory for 30 minutes per CD. Logins are never used; keep request volume user-initiated and low.
  - Wi-Fi sync to the iPhone app (`SyncProtocol.swift`, `SyncFiles.swift`, `SyncTransport.swift`, `SyncSession.swift`): the phone advertises `_musiclib-sync._tcp` over Bonjour while its Sync tab is open (`SyncAdvertiser`; the Mac browses with `SyncBrowser`), and the Mac connects with TLS on a pre-shared key (`SyncPairing.parameters`). Pairing derives the key from a 10-character code the phone shows (Crockford base32); inside that first session the Mac sends a random 256-bit key (`SyncGrant`) used from then on (in the keychain on both sides: `syncKey.<phone id>` on the Mac, `syncKey` on the phone). Messages (`SyncMessage`, JSON) and file data go in length-prefixed frames (`SyncFrame`). `SyncPlan` mirrors the selection: files under the managed folders (`Music`, `Artist Images`) the phone has but shouldn't are deleted, missing or different-size ones are sent; every album's `cover.jpg` and every artist photo are always wanted, so the whole library can be browsed; the database goes last as a snapshot without the catalog tables (`Database.writeSyncSnapshot`). Protocol version 3: the selection is a `SyncSelection` (ordered include/exclude rules over `ExportItem`s, now in Core; the last rule covering a song decides; `apply` compacts), the phone's manifest carries its `SyncRequest`s (Download / Remove from iPhone), which the Mac applies before planning (`SyncMacSession.sync(_:selection:…)`), and the phone can start a session: the Mac runs a `SyncAdvertiser(macID:phoneID:…)` (`_musiclib-mac._tcp`, that phone's key) per paired phone while it runs, and the phone browses for it while active (`PhoneSync.macPeer`, `requestSync`). A phone's first sync started from the phone adopts what's already on it into the selection instead of deleting. The Mac also sends `.concerts(SyncConcertSettings)`, and ownership is shown read-only on the phone (`AlbumOwnershipSection`: label number, date, price) and edited only on the Mac; phones before 1.18 could edit it, and their edits still arrive as `SyncEvent.Kind.purchase` (newer `album_ownership.updated_at` wins).updated_at` wins). Every path is untrusted on both ends: `SyncReceiver` (phone) only writes or deletes plain paths inside the managed folders (or `library.sqlite`), resolved with `LibraryPath.resolve`, via hidden `.mlsync` partials renamed into place. `SyncTests` run real TLS sessions over loopback. The Mac app's `SyncStore` (`AppModel.iPhone`, library access through `context`) keeps the iPhone selection (separate from the Export List), paired phones and runs syncs (`IPhoneSyncView`, sidebar **iPhone**; `AddToExportListButton` also offers Add to iPhone); the first sync to a phone asks before deleting. The phone's `PhoneSync` listens only while its Sync tab is visible. Two-way (protocol version 2, `SyncEvents.swift`): the phone records plays (the Mac's `ListenTracker` rules, saved when the song ends; one in progress when iOS ends the app is kept in `interrupted-play.json`) and like/unlike changes as `SyncEvent`s in its outbox (`SyncOutbox`, Application Support `sync-outbox.json`), overlays the likes on its copy's, and sends them with the manifest; the Mac applies them before writing the snapshot (`Database.applySyncEvents`: each event once via the `sync_events` table, only for a song whose ID and sha256 match, and only from the same library: `library_meta.library_id`, schema 14; the latest like change wins) and doesn't scrobble them (the phone does). The phone removes events once a sync finishes. When the Mac is connected to Last.fm and the phone's hello says it isn't, the Mac sends `.lastFM` and the phone adopts the account (`Scrobbler.adopt`). Both apps need `NSLocalNetworkUsageDescription` and `NSBonjourServices` with both service types (set in `scripts/build-app.sh` and `iOS/MusicLibraryMobile-Info.plist`).
  - `Concerts.swift`: upcoming concerts near home from Ticketmaster's Discovery API and JamBase's Concert Data API (free keys, in the keychain; `ConcertProvider`). Per artist (`upcomingConcerts`: Ticketmaster attraction matched by MusicBrainz ID or exact name, then events by `geoPoint` geohash; JamBase by `artistId=musicbrainz:<id>`, falling back to the name) and per library (`scan`: Ticketmaster searches every music event nearby month by month, splitting months over its 1,000-result cap; JamBase searches many `|`-joined names per request because its free plan allows 1,000 requests a month). `ConcertMerger` lists a show found by both once; `ArtistDirectory` matches listings to library artists. The ZIP code is located with `CLGeocoder` (`PostalCode.locate`). Fixtures `tm_*`/`jambase_*` follow the documented schemas (not captured). Error messages never include URLs (Ticketmaster's key is a query parameter). The app's `ConcertStore` (`AppModel.concerts`) caches results in `~/Library/Caches/MusicLibrary/concerts.json` (a day per artist, two for the library); `ArtistConcertsSection` is on artist pages, `ConcertsView` is the Concerts page, `ConcertSettings` the Settings tab. JamBase's free plan requires crediting it (`ConcertAttribution`).
- `Sources/MusicLibrary`: SwiftUI app (`AppModel`, `Player`, `ImportController`, views).
- `Tests/MusicLibraryCoreTests`: Swift Testing suites; fixtures in `Fixtures/`.

## Environment (Command Line Tools only; not needed with Xcode)
SwiftUI's `@State`/`@Environment` macro plugin is not shipped with the CLT, so the default macOS 27 SDK cannot compile the app target. Use the macOS 26 SDK:

    export SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk

`scripts/build-app.sh` does this automatically. Without Xcode, `Package.swift` adds the CLT swift-testing macro plugin path to the test target. `ToolLocator` finds ffmpeg/ffprobe/fpcalc first in the app's `Contents/Helpers` (built by `scripts/build-tools.sh`), then in /opt/homebrew/bin, /usr/local/bin or `PATH` (fpcalc optional); `MUSICLIB_TOOLS_DIR` goes before all of them. The bundled ffmpeg is a trimmed LGPL build (only the demuxers, muxers, codecs and filters the app's commands use, listed in the script): a new ffmpeg command may need a component added there. The tests make their audio with the installed ffmpeg (`TestSupport.tools`), and CI runs them again with `MUSICLIB_TOOLS_DIR=build/tools` so the code under test uses the bundled copies.

## Commands
- Build: `swift build`
- Test: `swift test` (needs ffmpeg; generates audio with `ffmpeg -f lavfi`)
- Live network tests (MusicBrainz, Cover Art Archive): `MUSICLIB_LIVE_TESTS=1 swift test --filter LiveTests`
- Rehearse the collection migration on a copy of a real library (migrated in place; refuses paths under `~/Music`; prints counts only): `MUSICLIB_MIGRATION_REHEARSAL=<copy>/library.sqlite swift test --filter MigrationRehearsalTests`
- Build app bundle: `scripts/build-app.sh` -> `build/MusicLibrary.app` (ad-hoc signed; `VERSION=…`, `BUILD=…`, `UNIVERSAL=1` for arm64 + x86_64, which needs Xcode; `SIGN_IDENTITY=…` signs with a certificate and the hardened runtime, plus a secure timestamp for a Developer ID one; one with a Team ID keeps keychain access across rebuilds; `BUNDLE_TOOLS=0` leaves out the tools)
- Build the app's ffmpeg, ffprobe and fpcalc: `scripts/build-tools.sh` -> `build/tools` (FFmpeg and Chromaprint from pinned, checksummed source releases; needs cmake; `UNIVERSAL=1`; reused until the script changes). `build-app.sh` runs it.
- Notarize: `NOTARY_PROFILE=… scripts/notarize.sh` (or `NOTARY_KEY`/`NOTARY_KEY_ID`/`NOTARY_ISSUER`) after building with a Developer ID `SIGN_IDENTITY`; staples the ticket. One-time setup: `docs/distribution.md`.
- Upload the iPhone app to TestFlight: `scripts/testflight.sh` (`UPLOAD=0` exports an .ipa instead; `VERSION=…`; `ASC_KEY`/`ASC_KEY_ID`/`ASC_ISSUER` for an API key; `DISTRIBUTION_CERTIFICATE=1` signs manually, as CI does, with the keychain's Apple Distribution certificate and "<bundle ID> App Store (CI)" profiles that `scripts/provisioning-profiles.swift` creates or renews through the API and installs; automatic signing can't be pointed at that certificate, and Xcode's cloud-signing profiles don't include it). Don't upload without being asked.
- Store a signing certificate as CI secrets: `scripts/set-signing-secret.sh "<identity prefix>" <SECRET_PREFIX>` (the user runs it: it exports from their keychain). CI imports them with `scripts/import-certificate.sh`.
- Regenerate the app icon (`Resources/AppIcon.icns`, `AppIcon-1024.png`, and the full-bleed, opaque iPhone and watch icons in their asset catalogs: iOS and watchOS mask the icon themselves and would show a transparent margin as a frame): `swift scripts/make-icon.swift` (needs the `SDKROOT` above).
- Run: `open build/MusicLibrary.app` or `swift run MusicLibrary`
- Regenerate the iPhone app's sample library: `scripts/make-sample-library.sh` (needs ffmpeg; about 23 MB, committed). The App Store listing, screenshots and review notes are in `docs/app-store/`.
- Build the website: `scripts/build-site.sh` -> `build/site` (`site/` plus the README screenshots and icon as WebP; needs cwebp). Preview with `python3 -m http.server -d build/site`.
- Build the core for iOS (needs Xcode): `xcodebuild -scheme MusicLibraryCore -destination 'generic/platform=iOS Simulator' build`
- Build the iPhone app (with its widgets and the embedded watch app): `xcodebuild -project iOS/MusicLibraryMobile.xcodeproj -scheme MusicLibraryMobile -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build` (or open the project in Xcode and run it on a simulator or the phone). Unsigned builds have no app group, so widgets stay empty; for the simulator sign to run locally: `CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=`.

## CI and releases
- `.github/workflows/ci.yml` builds, runs the tests (twice: with Homebrew's ffmpeg and with the app's, `build/tools`, cached by the build script's hash) and builds a universal app on every push and pull request (macOS runner, newest stable Xcode, ffmpeg from Homebrew). A separate `ios` job builds `MusicLibraryCore` and the iPhone app for iOS on GitHub's `xcode-27` image (Xcode 27, in preview; the macOS images stop at Xcode 26, without the iOS 27 SDK). That job and `testflight` use the release Xcode pinned as `RELEASE_XCODE` in `ci.yml` (`scripts/select-xcode.sh`, which lists the runner's Xcodes and fails if it's missing): App Store Connect won't submit builds from a beta Xcode, and the image doesn't name its betas as such (its `Xcode_27.2.app` was a beta). Bump it when a new release Xcode lands on the image.
- Pushing a tag `vX.Y.Z` also signs the app with the Developer ID certificate, notarizes it (secrets `DEVELOPER_ID_CERTIFICATE_P12`, `DEVELOPER_ID_CERTIFICATE_PASSWORD`, `NOTARY_API_KEY`, `NOTARY_API_KEY_ID`, `NOTARY_API_ISSUER_ID`; the build fails without them) and publishes a GitHub release with `MusicLibrary-X.Y.Z-macOS.zip` and its SHA-256. The `testflight` job (on `xcode-27`, after the build and iOS jobs) uploads the iPhone app as version X.Y.Z, signed with the `APPLE_DISTRIBUTION_CERTIFICATE_P12`/`_PASSWORD` certificate (the App Manager API key can't cloud-sign); running the workflow by hand with `testflight=export|upload` tests it without a tag. Its notes start with that version's section of `CHANGELOG.md` (or `## Unreleased` when there's none), then the install steps and GitHub's generated list of merged PRs.
- `CHANGELOG.md`: add user-visible changes under `## Unreleased` in the same PR as the change (plain bullets, absolute links: they're shown on GitHub's release page). Before tagging a release, rename `## Unreleased` to `## X.Y.Z`, add a new empty `## Unreleased` above it, and set `MARKETING_VERSION` in `iOS/Version.xcconfig` to X.Y.Z (CI takes the TestFlight version from the tag; this keeps local builds in step).
- The website (https://davidlago.github.io/music-library/) is plain HTML/CSS/JS in `site/` (no build tools or frameworks), published by `.github/workflows/pages.yml` on pushes to main that touch it, the screenshots or the icon. It uses the README's screenshots, so new ones show up there too; keep its feature copy in line with the README.
- README screenshots live in `docs/screenshots/` (1600 px wide, taken from a real library window). `iphone.png` and `iphone-dna-insights.png` are three iOS Simulator screenshots each (status bar set with `xcrun simctl status_bar … override --time 9:41`, taken with `xcrun simctl io booted screenshot`), put side by side on a 1600×1000 canvas by `swift scripts/compose-iphone-screenshots.swift <out> <left> <middle> <right>`; `iphone-widgets.png` is three home screen pages with the widgets. `watch.png` is up to four watch simulator screenshots (paired with the iPhone simulator; its status bar can't be overridden) in watch cases, by `swift scripts/compose-watch-screenshots.swift <out> <screens…>`.

## Library catalog
- The catalog site sits behind Cloudflare, which blocks URLSession (and curl) for pages and AJAX: `LibraryCatalogClient` loads them with `fetch()` inside a hidden `WKWebView` (persistent data store, so sign-ins survive), one request at a time with a short gap. Cover images (`bookcover.php`) redirect to other hosts, so they load with URLSession instead. Requests are `.interactive` (0.8 s apart) or `.background` (3 s apart: scans and lookups). A 429 sets a cool-down (Retry-After, or 60 s doubling up to 15 min) during which background work waits and interactive requests fail with `CatalogError.rateLimited`; background lookups also hold while a scan runs, so only one stream hits the site. Don't hammer the site while developing.
- `LibraryCatalogStore` (in `AppModel.catalog`) holds the query (persisted), client-side filters (ownership, "not on the shelf", which the catalog can't do), the account (password in the keychain), copies and the MusicBrainz lookup queue. Results' status ("On Shelf"…) is relative to the catalog site's own library. The list chosen in Settings (`listId`) is where Add to List goes; `listEntries` drive the bookmark badges and the list page.
- Downloaded catalog (`LibraryCatalogIndex.swift`, `LibraryCatalogDownload.swift`): every CD the libraries in `downloadLibraries` own is scanned page by page ("recently added" order) into `catalog_items` (`CatalogRecord.upsert` per page, so an interrupted scan resumes from `ScanState` in the cache; `CatalogRecord.prune` drops titles only after a complete scan), refreshed when older than 12 hours (at launch once something was downloaded, and when Library CDs opens), and looked up on MusicBrainz through `downloadQueue`, behind the user's own `lookupQueue`. `CatalogIndex` searches it in the app's query language (`SearchQuery`, with catalog meanings for `title:` = songs, `time:` = album length, `track:`/`disc:` = counts, `added:` = first seen) plus `CatalogSearchQuery` filters (`is:owned|available|out|onlist`, `library:`, `rating:`). Library CDs shows it when downloads exist; the live website search is its "Search the Whole Network Live" mode.
- Caching: MusicBrainz details in `catalog_info` (60 days; 14 for no match); covers and work pages on disk in `~/Library/Caches/MusicLibrary/Catalog` (`LibraryCatalogCache`); results pages for 30 minutes (Reload skips them); copies for 10 minutes in memory.

## Keychain
- `KeychainStore.app` keeps every secret in ONE generic-password item (`secrets`, a JSON dictionary) read once per launch: macOS asks to allow keychain access once per item for each new ad-hoc-signed build. Don't add separate items; older per-secret items are moved in when first read.

## Conventions
- UI layout: the player bar sits below the `NavigationSplitView`, not inside the detail column (views pushed on a `NavigationStack` draw over siblings in their column on macOS). Pages push `AlbumSummary`/`ArtistSummary` onto the single root stack via `NavigationLink(value:)`; don't nest another `NavigationStack`.
- `JewelCase` (album pages and the Albums grid) draws a cover as a CD in its jewel case; the Mac and iPhone apps each have a copy (`Sources/MusicLibrary/JewelCase.swift`, `iOS/MusicLibraryMobile/JewelCase.swift`), so change both. Pass `OwnershipMark(model.purchase(for:))` to `JewelCase(width:ownership:)`: a bought CD shows its label number on a `LabelSticker` across the top of the hinge (as on the real cases, reading bottom to top), a borrowed CD (not owned) an `OwnershipBadge` with arrow.left.arrow.right on the booklet, and a download one with dollarsign. Covers shown without a case take it as `CoverThumb`/`CoverImage` `ownership:` (label top-left, badges bottom-right; don't pass it to a cover inside a `JewelCase`).
- Views inside `Table` cells must not read `@Environment(AppModel.self)`: cells don't always receive it and the app crashes while scrolling. Pass the model, an object from it, or an action from the parent instead.
- Library layout: `<root>/Music/<AlbumArtist|Artist>/<Album> (<Year>)/<NN> - <Title>.<ext>`, DB at `<root>/library.sqlite`, track paths stored relative to root.
- Track paths come from a `library.sqlite` that may have been made elsewhere: read, copy, trash or export a track's file only through `Track.resolvedFileURL(root:)`/`coverURL(root:)` or `LibraryPath.resolve` (they reject `..`, absolute paths and symlinks leading outside the folder). `fileURL(root:)` is for display.
- `.TOC.plist` is read from every mounted volume (not only real CDs), so it is untrusted: `CDTOC.parse` rejects blocks outside the Red Book range (`CDTOC.maxBlock`) and non-increasing tracks; keep block arithmetic overflow-safe.
- Source files are never modified; tags are written only to the library copy (mp3, flac, m4a).
- MusicBrainz IDs from tags and `library.sqlite` are untrusted: `TagReader.parse` and DB row loading drop non-UUIDs via `TrackMetadata.validateMBIDs()`, and ID lookups build URLs with `MusicBrainzClient.lookupURL` (throws on invalid IDs). Never force-unwrap a URL built from an ID.
- Secrets (API keys, shared secrets, session keys) go in the keychain via `KeychainStore` (`Keychain.swift`), never in `UserDefaults`; values older versions left in defaults are moved over once with `migratedString(for:from:key:)`.
- MusicBrainz requests are rate limited (>=1.1 s) and identify the app with `AppInfo.userAgent`; tests must not hit the network unless `MUSICLIB_LIVE_TESTS=1`.
- Exported playlists: build `.m3u` text only with `PlaylistExporter.m3uContents`, which keeps tag/path line breaks (control characters, U+2028/U+2029) from starting new entries.
