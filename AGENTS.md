# Music Library – agent notes

Native macOS music library app (SwiftUI) built with SwiftPM only; no Xcode project, no third-party dependencies. Works with Xcode or just the Command Line Tools. MIT licensed.

`MusicLibraryCore` also builds for iOS 26, for the planned iPhone companion app (`docs/ios-companion-plan.md`). Parts that can't run there are wrapped in `#if os(macOS)`: running ffmpeg/ffprobe/fpcalc (`Tools.swift`, `TagReader`/`TagWriter`/`ImageTools`, `ImportService`, `AcoustIDClient`, `AlbumCover.swift`, `CDRipper`/`CDImporter`, `AccurateRipAudio.swift`), CoreAudio output switching and input devices (`CoreAudioOutput.swift`, `CoreAudioInput.swift`), `VinylImporter` and parsing library catalog pages (`LibraryCatalogParser.swift` uses `XMLDocument`; `CatalogEnricher.details`). Keep new Core code platform-neutral, or guard it the same way. `Database(snapshotAt:)` opens an exported or synced `library.sqlite` read-only (no migrations; refuses a newer schema).

The iPhone app (`iOS/MusicLibraryMobile.xcodeproj`, the repo's only Xcode project; the Mac app stays SwiftPM-only) depends on the local package for `MusicLibraryCore`. Its sources are a synchronized folder (`iOS/MusicLibraryMobile/`): new files there are picked up without editing the project. The target uses Swift 6 with main-actor default isolation, so code that runs off the main thread needs `nonisolated`. It reads the library from its Documents folder (`LibrarySnapshot`: the whole library with its cached artist/album info, photos, plays, play totals, the collection (`collection`, `collectionIndex`, `labelUnreadable`; `isEmpty` means no tracks and no items) and `CollaborationGraph`, plus `presentIDs`, the tracks whose files are on the phone: only those play (`playable`), the rest are dimmed and can be downloaded; `findRoot` accepts `Music Library`, Documents itself, or an export dragged in under any name) and reloads when the app becomes active. The app's minimum is iOS 26 (watchOS 26); iOS 27-only APIs need `#available` with an iOS 26 fallback (`PhonePlayer` uses iOS 27's audio session deactivation/resumption notifications, the interruption notification on 26), and building still needs the iOS 27 SDK. `PhonePlayer` (an `AVQueuePlayer`; background audio, lock screen controls) switches the audio session to each song's sample rate before playing it (off the main thread; the session is deactivated and reactivated when the rate differs from the last song's; `AVAudioSession.sampleRate` lags behind the hardware after a change, so the output shown is read again after playback starts), preloads the next song for a gapless transition only when it has the same rate, restarts the song at its rate when a DAC is plugged in mid-song, and pauses when it's unplugged. Open files with `AVURLAssetPreferPreciseDurationAndTimingKey` (AVFoundation otherwise estimates positions in FLAC files without a seek table) and seek the current item, not the queue player (a seek can otherwise land in the preloaded next song). `PhoneModel` overlays the outbox (likes, plays, and the `.purchase` events pre-1.18 versions left there, applied to the collection with `CollectionLegacy.overlay`) on the snapshot, computes Insights in the background, tracks `Availability` and download/remove requests (`SyncRequestQueue`, Application Support `sync-requests.json`; removing deletes the files at once with `SyncReceiver.delete`, covers stay), and wires the player to the shared `Scrobbler` (flushes on becoming active and when the network returns) and saves the queue to Application Support `player-state.json` (restored paused, like the Mac). Tabs (UI names; the `RootView.Tabs` raw values are stored as `selectedTab`, and `.insights` is Explore; 1.27's `library` and `sync` no longer decode, so those choices start over on Listen Now): Listen Now (`ListenNowTab.swift`, the default: `PhoneModel.listenNowAlbum`, the album playing or played last, tinted with `AlbumBackdrop`; `recentlyPlayedAlbums`, the album's labeled copy's shelf neighbors, `weekListening`/`loadWeekListening` (its own 7-day stats, so Insights keeps its period), the queue's `upcoming`; Sync and Settings buttons at the top), Collection (CDs and records first, then `DigitalCollectionCard`: All Music / On This iPhone, Albums, Songs, Liked Songs, Downloads, playlists; just `LibraryHome` when nothing is on the shelf; widget, watch and Siri links open albums and items here through `PendingAlbumOpener` and `PendingItemOpener`), Explore (Artists, which lists both collections' artists under All Music via `MusicCollection.artists(adding:)`, and Music DNA, then the Insights panes), Search. Sync is a sheet (`SyncTab`, `PhoneModel.showsSync`) opened from Listen Now or from a page asking to pair; user-visible text says Physical Collection / Digital Collection where they're meant apart and Local Library for the public library, while code identifiers keep their old names; every tab's stack is a `LibraryStack` (routes `LibraryRoute`, `AlbumSummary`, `ArtistSummary`, `DNARoute`, `QueryRoute`, `CollectionRoute`, `CollectionItemRoute`; `@Environment(\.openRoute)` pushes from menus). `AlbumPage`/`ArtistPage` mirror the Mac's pages (`AvailabilityBar` for Download/Remove), `MusicDNAViews.swift` and `InsightsViews.swift` (and its Listening/Owned files) port the Mac's; `PhoneConcerts` uses the concert settings the Mac hands over. Sample library (for App Review and anyone without the Mac app): `SampleLibrary.bundle` in `iOS/MusicLibraryMobile/` is a library folder made by `scripts/make-sample-library.sh` (the `SampleLibraryMaker` target: songs synthesized by `SongSynth`, covers and artist pictures drawn by `Artwork`, fictional artists in `SampleCatalog`, imported with `ImportService`, plus plays, likes, a collection written through the collection API (CD #1–#8 with #7 and #8 not ripped, Vinyl #1–#4 with #1 and #2 trackless and their covers in `Music/Collection Covers`, an album on both CD and vinyl, a download) and playlists). `PhoneModel.showSample` opens it read-only in place (`LibrarySnapshot(datesRelativeToNow:)` moves its history up to today) only while Documents has no library; `isSample` routes likes and plays to `sampleOutbox` (never synced), skips Last.fm, keeps its own player state and hides Download/Remove, and your own library arriving (or Hide) drops all of it (`forgetSample`). `SampleLibraryTests` open the committed bundle. Settings (gear on Listen Now and the Collection tab): appearance (`AppearanceMode`), sample-rate matching, output, Last.fm (the phone's own API key/secret and session, in its keychain). Signing: `iOS/Signing.xcconfig` includes the uncommitted `iOS/Local.xcconfig`, which holds `DEVELOPMENT_TEAM` (and, for a Personal Team, an `APP_BUNDLE_ID` unique to you; the targets' bundle IDs and `APP_GROUP_IDENTIFIER`, `group.$(APP_BUNDLE_ID)`, derive from it, so don't set `PRODUCT_BUNDLE_IDENTIFIER`). The app target's entitlements are `$(APP_ENTITLEMENTS)`: `AppGroup.entitlements` by default, `MusicLibraryMobile.entitlements` (plus iCloud, `ICLOUD_CONTAINER`) when `Local.xcconfig`, `scripts/testflight.sh ICLOUD=1` or the CI variable `ICLOUD` asks for it; widgets and the watch always use `AppGroup.entitlements`. The version of all four targets is `iOS/Version.xcconfig` (`MARKETING_VERSION`, kept at the Mac release's; `scripts/testflight.sh` sets the build number). `PrivacyInfo.xcprivacy` in `iOS/MusicLibraryMobile/` and `iOS/MusicLibraryWatch/` declares the required-reason APIs (user defaults, file timestamps, disk space) of the code in each, `MusicLibraryCore` included: declare any new one there. Free disk space may not leave the phone, so the Mac sends what a sync `needed` (`SyncPlanSummary`) and the phone refuses a sync that doesn't fit (`SyncHello.freeSpace` is only read from older phones).

Widgets and the Apple Watch app (same Xcode project): they show a `Glance`, a small Codable summary (library counts, `week`/`month` listening, owned albums, the optional `collection`, now playing, rediscover) in the Foundation-only `MusicLibraryGlance` package target (also `GlanceLink` `musiclibrary://` URLs, `GlanceCommand`, `GlanceMessage` keys, `GlanceFormat`), built by `Glance.build`/`Glance.nowPlaying` in Core (`GlanceBuilder.swift`, `GlanceTests`). The phone's `GlanceFeed` rebuilds it off the main thread (debounced; only Now Playing when just the player changed) and writes it with JPEG thumbnails named `Glance.coverName(albumKey:)` to `GlanceStore.shared` (`Glance/` in the app group container; the group ID is the Info.plist key `MusicLibraryAppGroup`), then reloads widgets, and `WatchLink` sends it to the watch (application context, plus a message while reachable; the watch asks for covers by message while the phone is reachable and gets 160 px JPEGs in the reply, a few per message). Commands (widget buttons, watch) go through `PhoneModel.perform`, which loads the library first (background launches) and writes the summary before returning (iOS reloads a widget right after its intent). Widget buttons are `AudioPlaybackIntent`s in `iOS/Shared/PlaybackIntents.swift` (compiled into the app and the iOS widget extension, which defines `WIDGET_EXTENSION`); they run in the app's process and use `PhoneModel.shared`, because SwiftUI may not have created the app yet. `iOS/MusicLibraryWidgets/` is compiled by both widget extensions (`MusicLibraryWidgets` for iOS: Listening, Now Playing, Physical Collection (`PurchasesWidget`, kind still `"Purchases"` so placed widgets survive), Rediscover, Digital Collection (`LibraryWidget`); `MusicLibraryWatchWidgets`: accessory families of Listening, Now Playing and Physical Collection), with `#if os(iOS)` around home-screen families and intents; those targets use Swift 6 without main-actor default isolation. `iOS/MusicLibraryWatch/` is the watchOS app (`WatchModel`: the summary in its own app group container for the complications, commands with replies; WatchConnectivity callbacks are `nonisolated`/`@Sendable`). The watch can't play music itself; it's a remote. Its Shelf page (`ShelfPage.swift`: `ShelfPage`, `WatchFindPage`, `ShelfItemPage`) finds labels offline in `GlanceShelf` (`shelf.json`, see the Collection bullet); Find's series and last numbers are kept in `watch-find.json` in its store, not in user defaults.

- `Sources/MusicLibraryCore`: all non-UI logic (SQLite, tags via ffprobe/ffmpeg, organizer, MusicBrainz/AcoustID/CoverArt clients, import, export, search, stats).
  - Search: `Search.swift` parses the query language (`SearchQuery`, filter keys in `SearchFilterKey.all`); `SearchIndex.swift` is an immutable in-memory index (matching, ranking, completions, spelling correction). The app rebuilds it off the main thread on every library reload; smart playlists are saved query strings evaluated against it.
  - `Appearance.swift`: `AppearanceMode` (System, Light, Dark), the only look setting, on the Mac and the iPhone (user defaults `appearance`). There are no custom themes (removed in 1.28): `AppearanceMode.resolve` maps a theme ID an older Mac stored under `theme` to its mode (light-and-dark themes to System, the rest to their one variant; `AppearanceTests` lists every 1.27 ID) and never writes the old key, so a downgrade keeps its theme. The Mac applies it with `NSApplication.appearance` (`AppModel.applyAppearance`), the phone by overriding its windows' interface style. Views use native colors (`AppColor` in `AppColors.swift`, `.secondary`, `.badge`); `RGB.swift` keeps the color math `ArtworkTint` uses.
  - `LastFM.swift`: signed Last.fm client (injectable transport for tests), `ListenTracker` (scrobble rules), `ScrobbleQueue` (persisted to Application Support). `Scrobbler.swift` (`@Observable`, shared by the Mac and iPhone apps) connects them to the player: account (browser authorization through an injected `openURL`), now playing, the queue with retry and backoff.
  - `ArtistInfo.swift`: artist info from MusicBrainz (url-rels, genres), Wikidata, Wikipedia summaries and Last.fm; pure parsers and `ArtistInfo.assemble` are tested with real fixtures, `InfoFetcher` does the network calls (artists and albums). `ArtistResolver` picks the MusicBrainz artist (multi-artist credits need a confident name match). The app's `ArtistInfoStore` caches it in the `artist_info` table and `<root>/Artist Images`. External URLs (MusicBrainz relations, Wikipedia/Last.fm pages, and anything read back from the `artist_info`/`album_info` caches) are untrusted: parse them with `URL(webLink:)` and only pass `url.webLink`/`isWebLink` URLs (http/https with a host) to `Link`/`openURL`.
  - `ArtistPhotos.swift`: photos the user can pick for an artist. `ArtistPhotoFinder` (injectable transport) searches Deezer's artist API (no key; pictures with an empty image hash are placeholders) and Wikimedia Commons, and lists the artist's linked Deezer artist (MusicBrainz url-rel) and Wikipedia article images first; Wikimedia files are resolved to a 1200 px rendition when picked. Only https images from Deezer/Wikimedia hosts are downloaded (`ArtistPhotoParser.isPhotoURL`). Fixtures `deezer_*`, `wp_images_*`, `commons_search_*` are real responses. The chosen photo (`ArtistPhotoChoice`) is saved in the `artist_photos` table, apart from `artist_info`, so updating the info never replaces it; its file goes in `Artist Images` under a new name each time (views reload by file name), and rows are untrusted (`isSafeFileName`). The app's `ArtistPhotoSheet` (artist page: toolbar, hover on the photo, or dropping an image on it; artist grid context menu) shares file/drag/clipboard loading with `AlbumCoverSheet` via `ImageInput`; show photos with `ArtistInfoStore.imageFile(for:)`/`imageURL(for:)`, which prefer the chosen photo.
  - `AlbumInfo.swift`: album info from the MusicBrainz release group (rating, filtered genres, review links), the matched release's track list, Wikipedia and Last.fm; `AlbumTracklist.merge` lines the release up with the library's tracks. Cached in `album_info` by `AlbumInfoStore` (opening an album fetches it first).
  - `MusicDNA.swift`: `CollaborationGraph`, people from credits/tags/track artists (merged by MusicBrainz ID, then normalized name; non-musical release credits like photography are skipped) linked by shared tracks, plus the capped breadth-first neighborhood and radial layout shown on the Music DNA page. Rebuilt with the search index. In the UI, show people's names with `PersonLink`/`PersonLinks`/`PeopleRow` (pass `model.showMusicDNA` as `open`) so they open Music DNA.
  - `PlayQueue.swift`: the Spotify-style play queue (the list playback started from, plus songs queued with Play Next, which always play next; Add to Queue appends to the end). `Player` wraps it; `QueueView` shows it in a fixed-width pane beside the split view (not an `.inspector`, which makes macOS 27 loop through constraint passes until AppKit throws). The queue and position are saved on quit (and at each track change) as a `PlayQueue.Snapshot` of track IDs in Application Support (`player-state.json`, `AppModel.savePlayerState`) and restored paused at launch; a restored song isn't loaded (no output-format change, no play recorded) until it's played.
  - Liked songs: the `liked_tracks` table (track id, liked date; cascades when a track is removed), `AppModel.likedDates`/`setLiked`. Liked Songs is a built-in playlist (`SidebarItem.likedSongs`, `ExportItem.likedSongs`, most recently liked first) that can't be renamed or deleted. Show the heart with `LikeButton(model:track:)` (safe in `Table` cells) and `LikeMenuButton` in song context menus.
  - Listening history: the `plays` table (one row per listen, `counted` = met the scrobble rule), recorded by `AppModel` from player events.
  - `LibraryExport.swift`: `LibraryExporter` copies tracks to another folder using the library's layout (data only, via a hidden partial file and a rename; it never overwrites or deletes), writes `Playlists/*.m3u`, and can replace `<dest>/library.sqlite` with a `VACUUM INTO` snapshot (bringing `Artist Images` up to date with it). `ExportPreview` scans a destination's `Music` folder and merges it with the plan, per album folder, for the Export List's split view. The app's Export List (`ExportItem`, `ExportViews.swift`) collects albums, songs, artists and playlists and resolves them to tracks at export time; the destination is a setting (`AppModel.exportDestination`). `PlaylistExporter` (in `Import.swift`) is the older one-folder-per-playlist export.
  - `LibrarySort.swift`: `AlbumSort`, the Albums grid's orders on the Mac and iPhone (`albumSort`), and `SongSort`, the iPhone Songs list's (the Mac song table's columns plus Date Added; empty values last, ties in library order).
  - `Stats.swift`: `LibraryStats`, everything shown in the Digital Collection pane of Insights, computed in one pass with data-driven list sizes and bucket granularity.
  - `ListeningStats.swift`: `ListeningStats`, the Listening pane of Insights, from the `plays` rows (`Database.plays()`) for one period (7 days, 30 days, 12 months, all time): top songs/artists/albums/genres (artists and albums carry a `trackId` for their cover), activity over time, the same-length window before (`previous` totals and `previousActivity`, bucket for bucket; nil/empty for all time or without history that far back), artists/albums/songs first heard in the period, a weekday × hour clock and plays per hour, eras vs the library (each with its top album), skips, streaks and forgotten favorites. The pane (`ListeningInsightsView.swift` on the Mac, `ListeningInsightsViews.swift` on the iPhone, kept alike) is a listening report: a banner over the blurred top artist photo, Top Charts with pictures, New to You, Patterns, Quick Facts; panels take their color from a picture with `ArtworkTint` (Core: average color, darkened for white text). `AppModel.loadListeningIfNeeded` computes it in the background and refreshes it when `historyVersion` (bumped per recorded listen) changes.
  - `AlbumOwnership.swift`: the pre-collection ownership types that stay for compatibility: `AlbumPurchase` (one `album_ownership` row: album, artist, `format` CD or download, purchase day, price, CD `labelNumber`; also the Codable payload of pre-1.18 phones' `SyncEvent.Kind.purchase`, which carries no format or label), `TrackPurchase` (songs bought as downloads, entered on the Import page, per song or a batch total split with `TrackPurchase.split`; `track_purchases`, created on open, cascades with the track) and `PurchaseDay` (a calendar day with no time zone; also used by Concerts). Prices are `Decimal`, stored as POSIX decimal text in the locale's currency (`currencyCode` in the app). `album_ownership`'s `label_number` and `format` (NULL = CD) were added on open without a schema version change, so `albumPurchases`/`legacyOwnershipRows` read snapshots without them. Rows are untrusted and read back with bad dates/prices as unknown. What you own now lives in the collection (next bullet); nothing new reads `album_ownership` except the migration and reconcile.
  - Collection (`Collection.swift`, `CollectionStore.swift`, `CollectionLegacy.swift`, `CollectionCovers.swift`, `CollectionSearch.swift`, `CollectionStats.swift`, `CollectionLookup.swift`; design and decisions in `docs/physical-collection-plan.md`): everything you own, with or without tracks. `collection_items` (created on open, `user_version` stays 14; no UNIQUE index on labels, since legacy data may repeat a number) holds one `CollectionItem` per copy: `CollectionMedium` (`cd`, `vinyl`, `download`, or `.other(raw)` written by a newer version: shown, read-only, never projected), a `stickerNumber` in the medium's `StickerSeries` (CD and vinyl, each 1…9,999,999; a `Sticker` always shows with its series, "CD #12"/"Vinyl #12"; in code it's a sticker so `label:` keeps meaning the record label, which the UI calls **Record label**), release fields, purchase day and price, notes, `cover_file`, and the `album_key` (`SearchIndex.albumKey`) of its digital copy plus `digital_source` (`rip`, `download`, `same`, NULL = never linked); `DigitalState` is always derived from the tracks under the key, never stored. Ids are lowercased UUIDs, except migrated rows' deterministic `own-<FNV-1a 64 hex of the key>` (the phone synthesizes the same ones from an older snapshot); downloads derived from `TrackPurchase`s (`songs-<hex>`, `origin == .songs`) are computed in `MusicCollection` and never stored. `MusicCollection` is the immutable lookup (copies per key, `items(at:)`, `neighbors(of:)`, `nextNumber(in:)`, gaps, duplicates, `mark(albumKey:)` → `CopyMark`, `matches(...)`, `syncItems(_:)`), rebuilt off the main thread with the search index; `CollectionLinker.changes` backfills release IDs (never another copy's release) and the inferred source after a reload and relinks only by exact release ID. Rows are untrusted (`collectionItems()` probes the columns, validates each, and drops and counts what it can't read in `unreadable`). Write only through `saveCollectionItem(s)`/`deleteCollectionItem`/`applyCollectionChanges`/`rekeyCollection` (`updatedAt` is the user's last edit: linker changes and rekeys keep it).
  - Collection compatibility (`CollectionLegacy`): `album_ownership` is now a projection the Mac writes (`projectLegacyOwnership`) for 1.14–1.20 phones and older Macs after a downgrade: per album key, only the primary copy (lowest-labeled CD, any CD, then a download), with its own date and price; `format` is only ever NULL or `'digital'` and `label_number` only holds CD numbers; vinyl, `.other` and derived downloads are never projected. `migrate()` runs `reconcileLegacyOwnership` (rows that aren't what the projection wrote are an older app's edit, whatever their time, and are copied into the primary copy; a missing row never deletes an item), then the projection, then `markLegacyWriters` once: the table is remade (same rows, rowids and columns) with defaults no app writes (`format` 'pre-1.19', `label_number` 'unwritten', which the `album_ownership_writer` trigger turns into NULL with `format` 'pre-1.18'), so reconcile can tell a column an older app left out from one it cleared (`CollectionLegacy.Writer`); every reader takes both markers for a CD. Any new writer of `album_ownership` must name every column (`saveAlbumPurchase` is the tests' stand-in for older writers). Pre-1.18 phone events (`.purchase`) change only the primary CD/download copy's date and price (`applyLegacyPurchase`; a nil one deletes only an unlabeled copy; vinyl is never touched); the phone applies the same rules in memory (`CollectionLegacy.overlay`). Guarded by `LegacyLibraryMigrationTests` (libraries made by the released code of 1.14–1.20 in `Fixtures/legacy-libraries`: every pre-existing row byte-identical by rowid, each ownership row one item with its own values and legacy id, song purchases as derived downloads, idempotent reopen, older readers' exact SELECTs unchanged, a phone reading the unmigrated copy agreeing with the Mac), `DowngradeRoundTripTests` (the exact 1.17, 1.18 and 1.20 writes on a migrated library: cleared labels stay cleared, a download made a CD stays one, earlier clocks taken in, marking once), the opt-in `MigrationRehearsalTests` (see Commands) and `CollectionStoreTests.olderReadersSeeTrueData` (the exact 1.17, 1.18 and 1.19/1.20 SELECTs on a projected library); `LegacyOwnership.swift` keeps private copies of 1.20's ownership algorithms to compare against. These must stay green and must never be weakened.
  - Collection covers: an item's own cover is `Music/Collection Covers/<item id>-<8 hex>.jpg` (a new name on each change; `CollectionCovers.write`/`adopt`, names checked with `CollectionCovers.isFileName`, resolved with `LibraryPath.resolve`); NULL means the linked album's `cover.jpg`. Removing an album from the library first has its items adopt the album's cover and clears their source. The folder is under `Music`, so `SyncPlan` (`collectionCovers:`, always wanted, like album covers) and older phones' `SyncReceiver` accept it with no protocol change; `LibraryExporter` copies them with the database; the Organizer never writes there.
  - Collection search (`CollectionSearch.swift`): `CollectionSearchQuery.parse` peels the collection keys off and hands the rest to `SearchQuery.parse`: `own:` (`medium:`/`media:`; cd, vinyl/lp/record, download, physical, any, none), `ripped:` (yes, no, partial, missing, other), `sticker:` (`12`, `cd100-199`, `vinyl>=50`, `none`), `bought:`, `paid:`, `copies:`, `barcode:`, `catno:`, plus the `#12`/`cd#12`/`vinyl#12` shorthand (search boxes only; songs and saved smart playlists read it as text, and `canonical` saves it as `sticker:`). None of them are in `SearchFilterKey.all`, and nothing is added to `is:`, `missing:` or `has:` (an older reader turns an unknown key into text that matches nothing, but drops an unknown `is:` value and would match everything). Collection filters apply across the whole query. `CollectionIndex` matches items (their fields, album info and linked tracks); `LibrarySearch.run`/`tracks(matching:)` is the one entry point for search boxes and smart playlists (queries without collection keys give exactly `SearchIndex`'s results: golden tests in `CollectionSearchTests`), with `labelHits` when the whole query is a label. In the downloaded library catalog (Local Library CDs), `own:` means you own it while `is:owned` keeps meaning in your digital collection (`CatalogSearchContext.collection`).
  - `CollectionStats` is the Owned pane of Insights (CDs, records and downloads; raw value `InsightsView.Pane.owned = "Owned"`, so stored choices and `GlanceLink.insights(.owned)` keep working): counts per medium and digital state, `SeriesStats` per series (next, gaps, duplicates), spending by medium over time, value per album key (plays counted once per key), lists and facts. `CollectionLookup.swift`: adding by barcode, words or catalog number (`CollectionReleaseQuery`, `MusicBrainzClient.searchEditions`, `CollectionEditionParser`, `CollectionDraft`). `Discogs.swift`: the same on Discogs for editions MusicBrainz doesn't list (`DiscogsClient`, no key: about 25 requests a minute, so it keeps to 20 in any minute and a 429 is `DiscogsError.busy`; `searchEditions` also takes a pasted release link, `DiscogsLink`; `DiscogsParser`, fixtures `discogs_*` are real responses; search results have no pictures without an account, so the sheet looks the release up when it's picked, `EditionSearch.details`). Discogs editions are `CollectionEdition`s with `discogsReleaseID` (id `discogs-<n>`, never an MBID; grouped by master). The item keeps it as `discogsReleaseID` (`collection_items.discogs_release_id`, added on open; older versions' upserts keep it), and with no MusicBrainz release its track list comes from `DiscogsRelease.releaseInfo` (no MusicBrainz IDs; sides two to a disc on a multi-record set) for album info (`InfoFetcher.fetchAlbum(discogsReleaseId:)`) and Digitize Vinyl. `EditionSearch.source` (user defaults `editionSearchSource`) picks MusicBrainz or Discogs in Add to Collection and Change Edition….
  - Sync to Discogs (`DiscogsCollection.swift`; Mac only): sends the CDs and records (`DiscogsReleaseMatcher.isSynced`: stored, `.cd`/`.vinyl`) to the user's Discogs collection, one way (nothing from Discogs changes the collection). `DiscogsCollectionClient` is the authenticated API (personal access token in the keychain, `DiscogsToken.keychainAccount`, cleaned to letters and digits before it goes in a header; usernames checked with `DiscogsIdentity.isValidUsername` before they go in a path; injectable transport; 50 requests in any minute, Discogs allows 60; 401/403 is `DiscogsError.unauthorized`, which stops a sync; removing a copy already gone counts as removed): identity, folders, the collection (folder 0, all pages), add to a folder (never 0), remove an instance from its own folder, barcode search. An item's release is its `discogsReleaseID`, else its MusicBrainz release's Discogs url-rel; otherwise `DiscogsReleaseLookup.match` gathers `DiscogsEditionFacts` (the item's barcode, catalog numbers, country and year, filled in from `MusicBrainzClient.editionFacts`, which also gives the release group's Discogs master: few releases link a Discogs release, most release groups link a master, and most items have no barcode of their own) and tries a barcode search, the master's versions (`DiscogsCollectionClient.versions`), a catalog number search, then artist and title; search results (barcode ones too: Discogs matches barcodes loosely) count only when `isSameAlbum`. `DiscogsReleaseMatcher.best` scores candidates (barcode, catalog number exact or contained, country with ISO codes mapped to Discogs' names by `discogsCountries`, year, not a repress, exact title) instead of requiring one, and the match carries a `DiscogsMatchQuality` (`exact`, `edition`, `closest`: shown as Closest edition in the sheet). Matches are saved per item in `discogs_sync` with the `basis` they were made from, their quality and the `matcher` version (looked up again when the edition changes, after 30 days with no match, or when `DiscogsReleaseMatcher.version` is newer than what found nothing). `DiscogsMatchRehearsalTests` (opt-in, `MUSICLIB_DISCOGS_REHEARSAL=<copy>/library.sqlite`, live and without a token) prints what the matcher finds for a real collection. `DiscogsSyncPlan.make` links items to instances: linked copies first (kept even when no release is matched now), then each other item takes an unlinked copy of its release (so a first sync never duplicates what's there) or is added; every unclaimed copy is a removal (only on Discogs, removed here, old edition), which the sheet never ticks for the user. `DiscogsSync.run` saves each link as it's made. `discogs_sync` (item id, match, and the linked account/instance/release/folder) is Mac-only, created on open without a schema change, outlives its items (so a removed item's copy can be offered for removal), is untrusted when read, and is emptied in phone snapshots. ## Environment (Command Line Tools only; not needed with Xcode)
SwiftUI's `@State`/`@Environment` macro plugin is not shipped with the CLT, so the default macOS 27 SDK cannot compile the app target. Use the macOS 26 SDK:

    export SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk

`scripts/build-app.sh` does this automatically. Without Xcode, `Package.swift` adds the CLT swift-testing macro plugin path to the test target. `ToolLocator` finds ffmpeg/ffprobe/fpcalc first in the app's `Contents/Helpers` (built by `scripts/build-tools.sh`), then in /opt/homebrew/bin, /usr/local/bin or `PATH` (fpcalc optional); `MUSICLIB_TOOLS_DIR` goes before all of them. The bundled ffmpeg is a trimmed LGPL build (only the demuxers, muxers, codecs and filters the app's commands use, listed in the script): a new ffmpeg command may need a component added there. The tests make their audio with the installed ffmpeg (`TestSupport.tools`), and CI runs them again with `MUSICLIB_TOOLS_DIR=build/tools` so the code under test uses the bundled copies.

## Library catalog
- The catalog site sits behind Cloudflare, which blocks URLSession (and curl) for pages and AJAX: `LibraryCatalogClient` loads them with `fetch()` inside a hidden `WKWebView` (persistent data store, so sign-ins survive), one request at a time with a short gap. Cover images (`bookcover.php`) redirect to other hosts, so they load with URLSession instead. Requests are `.interactive` (0.8 s apart) or `.background` (3 s apart: scans and lookups). A 429 sets a cool-down (Retry-After, or 60 s doubling up to 15 min) during which background work waits and interactive requests fail with `CatalogError.rateLimited`; background lookups also hold while a scan runs, so only one stream hits the site. Don't hammer the site while developing.
- `LibraryCatalogStore` (in `AppModel.catalog`) holds the query (persisted), client-side filters (ownership, "not on the shelf", which the catalog can't do), the account (password in the keychain), copies and the MusicBrainz lookup queue. Results' status ("On Shelf"…) is relative to the catalog site's own library. The list chosen in Settings (`listId`) is where Add to List goes; `listEntries` drive the bookmark badges and the list page.
- Downloaded catalog (`LibraryCatalogIndex.swift`, `LibraryCatalogDownload.swift`): every CD the libraries in `downloadLibraries` own is scanned page by page ("recently added" order) into `catalog_items` (`CatalogRecord.upsert` per page, so an interrupted scan resumes from `ScanState` in the cache; `CatalogRecord.prune` drops titles only after a complete scan: `CatalogScan` keeps the largest count any page reported, treats an empty or shrunken page before the end as the site struggling (read again after a pause, then the scan stops and resumes later) and refuses to prune a scan that saw well short of the count or under half of what the library had), refreshed when older than 12 hours (at launch once something was downloaded, and when Local Library CDs opens), and looked up on MusicBrainz through `downloadQueue`, behind the user's own `lookupQueue`. `CatalogIndex` searches it in the app's query language (`SearchQuery`, with catalog meanings for `title:` = songs, `time:` = album length, `track:`/`disc:` = counts, `added:` = first seen) plus `CatalogSearchQuery` filters (`is:owned|available|out|onlist`, `library:`, `rating:`). Local Library CDs (sidebar section Local Library, Settings tab Local Library) shows it when downloads exist; the live website search is its "Search the Whole Network Live" mode.
- Caching: MusicBrainz details in `catalog_info` (60 days; 14 for no match); covers and work pages on disk in `~/Library/Caches/MusicLibrary/Catalog` (`LibraryCatalogCache`); results pages for 30 minutes (Reload skips them); copies for 10 minutes in memory.

## Keychain
- `KeychainStore.app` keeps every secret in ONE generic-password item (`secrets`, a JSON dictionary) read once per launch: macOS asks to allow keychain access once per item for each new ad-hoc-signed build. Don't add separate items; older per-secret items are moved in when first read.

## Conventions
- UI layout: the player (`NowPlayingBar`) is a capsule floating over the bottom of the pages as an overlay on the `NavigationSplitView`, offset past the sidebar's measured width, not inside the detail column (views pushed on a `NavigationStack` draw over siblings in their column on macOS). Every page root on the stack takes `.playerClearance()` (bottom safe-area padding of `NowPlayingBar.clearance`) so its last row scrolls clear of the player: a modifier on the `NavigationStack` itself doesn't reach pushed pages on macOS, so a new `navigationDestination` needs it too. Album, artist, item and Listen Now pages are tinted by their artwork with `AlbumBackdrop`. Pages push `AlbumSummary`/`ArtistSummary` onto the single root stack via `NavigationLink(value:)`; don't nest another `NavigationStack`.
- `JewelCase` (CDs) and `RecordSleeve` (vinyl) draw a cover the way the copy sits on the shelf; the Mac and iPhone apps each have a copy of them and of `LabelSticker`, `StickerPill`, `CopyBadge` and `CoverCopyMark` (`Sources/MusicLibrary/JewelCase.swift`, `RecordSleeve.swift`, `Support.swift`; `iOS/MusicLibraryMobile/JewelCase.swift`, `RecordSleeve.swift`, `CoverImage.swift`), so change both. Pass a `CopyMark` (`model.collection.mark(albumKey:)`/`mark(item:)`, or `model.copyMark(for:)`) to `CopyArt(mark:url:width:)`, which picks the case, the sleeve or a flat cover, or to `JewelCase(width:mark:)`/`RecordSleeve(width:mark:)`: a CD's label is a `LabelSticker(number:series: .cd)`, the white strip across the top of the hinge reading bottom to top; a record's is `LabelSticker(series: .vinyl)`, the same white strip in the same place and size down the sleeve's left edge (number only on both: the case or sleeve tells the series; on the Mac, hovering the sticker or a badge shows what it means); an undigitized copy gets a `waveform.slash` badge, a download `dollarsign`, an album not in the collection the Borrowed badge (arrow.left.arrow.right). Sticker colours are fixed, the same in light and dark. In lists and captions show a label with `StickerPill(sticker:)`, never a bare number. Covers shown without a case take the mark as `CoverThumb`/`CoverImage` `mark:` (`CoverCopyMark`: pill top-left, badges bottom-right; don't pass it to a cover inside a case or sleeve).
- Views inside `Table` cells must not read `@Environment(AppModel.self)`: cells don't always receive it and the app crashes while scrolling. Pass the model, an object from it, or an action from the parent instead.
- Library layout: `<root>/Music/<AlbumArtist|Artist>/<Album> (<Year>)/<NN> - <Title>.<ext>`, DB at `<root>/library.sqlite`, track paths stored relative to root.
- Track paths come from a `library.sqlite` that may have been made elsewhere: read, copy, trash or export a track's file only through `Track.resolvedFileURL(root:)`/`coverURL(root:)` or `LibraryPath.resolve` (they reject `..`, absolute paths and symlinks leading outside the folder). `fileURL(root:)` is for display.
- `.TOC.plist` is read from every mounted volume (not only real CDs), so it is untrusted: `CDTOC.parse` rejects blocks outside the Red Book range (`CDTOC.maxBlock`) and non-increasing tracks; keep block arithmetic overflow-safe.
- Disc names: macOS names an audio CD's volume after its album and the track files after its songs ("1 Somewhere, My Love.aiff"), from the disc's CD-Text or Apple's Gracenote lookup (whose cache, `com.apple.iTunes.Gracenote.plist`, holds only opaque IDs), and the volume name often runs artist and album together; "Audio CD" and "1 Audio Track.aiff" mean no names. `CDNames.read` (`AudioCDVolume.names`) turns them into a title and song titles, which seed the CD page's rows and album search until MusicBrainz matches, and title Rip to Import Queue files; `CDController.nameDisc` splits the title into artist and album with `CDNames.split` (an artist in your collections, else MusicBrainz's best match from `searchArtists(in:)`), never over fields the user edited. They're untrusted like the TOC: cleaned and capped by `CDNames.clean`, and through `Organizer.sanitize` before a path. A disc MusicBrainz doesn't know (`CDDisc.isUnmatched`) is ripped straight into the library once the page names its album (`canRipUnmatched`): `CDController.tagging` gives each track `TrackMetadata.unmatchedDisc` (the page's album, artist and editable row title) instead of the release's song, through the same rip loop and `CDImporter.ripAndImport(metadata:)`. It can also be cataloged: `saveUnmatched` adds a new CD named by the page's album/artist fields, with the cover chosen on the page (`CDCoverSheet`, whose Cover Art Archive search is the reusable `CoverSearchPane`; `CDController.setCover`), and Rip to Import Queue links the rip to it (`importLinkItemID`).
- Source files are never modified; tags are written only to the library copy (mp3, flac, m4a).
- MusicBrainz IDs from tags and `library.sqlite` are untrusted: `TagReader.parse` and DB row loading drop non-UUIDs via `TrackMetadata.validateMBIDs()`, and ID lookups build URLs with `MusicBrainzClient.lookupURL` (throws on invalid IDs). Never force-unwrap a URL built from an ID.
- Secrets (API keys, shared secrets, session keys) go in the keychain via `KeychainStore` (`Keychain.swift`), never in `UserDefaults`; values older versions left in defaults are moved over once with `migratedString(for:from:key:)`.
- MusicBrainz requests are rate limited (>=1.1 s) and identify the app with `AppInfo.userAgent`; tests must not hit the network unless `MUSICLIB_LIVE_TESTS=1`.
- Exported playlists: build `.m3u` text only with `PlaylistExporter.m3uContents`, which keeps tag/path line breaks (control characters, U+2028/U+2029) from starting new entries.
